# Carp Strategy Dev

本 skill 用于约束本项目中的策略研发与执行方式。

## 工作总原则

- 以目标达成为第一优先级。
- 不要停留在分析层面，如果可以通过修改代码、运行验证、对比结果来推进，就直接推进。
- 不因一次失败就停止。
- 不因结果不理想就草率结束。
- 优先行动、验证、回退、再尝试，而不是长时间空想。
- 必须诚实：如果验证结果不好，就明确说明不好，不能强行解释成有效。

## 核心目标

所有工作都应围绕用户当前目标推进，例如：

- 提升 `return`
- 提升 `tPF`
- 提升 `median`
- 降低亏损股票数量
- 修复被新策略打坏的股票
- 改善买卖点匹配
- 优化路由、风控、持有逻辑
- 清理项目文档和工程结构

不围绕边缘问题发散，不偏离当前目标。

## 默认执行循环

1. 先确认当前保留基线。
2. 明确这一步要优化的具体目标。
3. 先做根因分析，确认问题真正落在哪个家族、哪条退出链、哪一批股票或哪类坏簇。
4. 提出下一条窄而清晰的假设。
5. 直接在主工作文件中修改代码，除非有充分理由不这么做。
6. 运行正式验证。
7. 与当前基线对比。
8. 如果结果更好，就保留并继续往下一层挖。
9. 如果结果更差、无增量或副作用过大，就完整回退。
10. 重复以上循环，直到达到目标或确认该方向无优化空间。

## 根因优先规则

- 修改代码之前，必须先尽量分析清楚根本原因。
- 优先回答“为什么会这样”，再回答“怎么改”。
- 不要一上来就调参数。
- 如果根因还不清楚，优先做：
  - 真实交易簇归因
  - 受损股票对比
  - 入场/退出分支定位
  - 因子分布对比
  - 运行时路径核对
- 只有在已经明确问题落点后，才做有针对性的修改。

## 策略设计约束

- 新策略不能只设计入场方案，必须同时考虑配套出场方案。
- 任何新的买点、路由分流、策略家族或持有模式，在进入正式实验前，都应同时回答：
  - 这类单子为什么买
  - 买后什么情况下继续拿
  - 买后什么情况下尽快退出
  - 它与现有止损、trailing、extended hold、趋势转空退出如何配合
- 如果只补买点、不补卖法，常见结果是：
  - 买入后立即卖出
  - 无端被硬止损打掉
  - 被不匹配的旧退出链截胡
- 所以凡是“新家族 / 新买点 / 新路由”实验，都应默认把“配套退出方案”视为同一项设计任务，而不是后补项。

## 探索信息源

- 探索阶段可以主动借助外部信息源，包括：
  - Google 搜索
  - GitHub 搜索
  - 项目内因子库
  - 项目历史报告
  - 现有测试与验证脚本
- 使用外部搜索时，目的不是照抄策略，而是：
  - 帮助确认模式是否常见
  - 借鉴更合理的结构设计
  - 帮助解释为什么某类走势不适合当前逻辑
- 使用项目内信息时，优先看：
  - `factor_library.py`
  - 正式报告
  - 真实 `entry_reason / exit_reason`
  - 已保留基线与受损股票名单

## 因子库规则

- `stock_trading_advisor/src/factor_library.py` 是本项目动态更新的因子兵工厂。
- 如果在网络搜索、GitHub、论文、策略文章或其他外部资料中发现了对本项目有价值的有效因子，应优先考虑把它沉淀进 `factor_library.py`。
- 不要把有效因子长期散落在：
  - 临时脚本
  - 临时研究代码
  - `new_strategy.py` 中的局部一次性计算
- 更推荐的做法是：
  1. 先确认因子定义与本项目问题相关
  2. 确认它可以无未来函数地计算
  3. 加入 `factor_library.py`
  4. 再在研究或策略逻辑中调用
- 这样做的目标是：
  - 让因子积累成为可复用资产
  - 方便后续 session 继续扩展
  - 避免同类因子被重复临时实现

## 禁止的低质量推进方式

- 不分析根因就直接调参
- 因为某个猜测“听起来合理”就直接改主线
- 没区分问题是在：
  - 入场
  - 持有
  - 退出
  - 路由
  - 风控
  就开始大范围改动

## 基线纪律

- 任何时候都要知道当前“保留版”是什么。
- 所有实验都必须与当前保留基线对比，而不是凭记忆判断。
- 实验失败必须完整回退。
- 不允许把失败实验半留在代码里。

## 验证纪律

- 优先使用项目正式验证路径，不使用未经确认的临时判断代替。
- 能跑正式回测，就不要只做局部猜测。
- 当改动针对特定股票或坏簇时，要显式检查这些目标对象。
- 当改动只修某一只股票、某一类股票或某一类坏簇时，必须额外显式检查：
  - 高收益前排股票
  - 被新改动打坏的股票
  - losers 数量
- 必须区分：
  - 局部改善
  - 可以正式保留的全局改善

仅仅救了一只股票，不代表这次改动可以保留。

## 分层验证策略

- 针对某一只或某一类股票的优化，不要一上来就直接全量回测。
- 更高效的默认路径是：
  1. 先深入分析目标股票或目标类型的根本原因
  2. 针对性设计策略或修改分支
  3. 先做单一股票验证
  4. 再做同类型股票验证
  5. 再扩到更多相近股票验证
  6. 最后再做全部股票正式回测验证
- 如果在某一层验证就出现明显问题，不要硬推进到下一层，而应回到根因分析阶段，重新研究：
  - 因子库
  - 历史报告
  - 网络搜索
  - 真实交易簇
- 这条分层验证路径的目标是：
  - 更快筛掉坏方向
  - 更早发现策略是否只对单股有效
  - 避免把明显不稳的方向直接带进全量回测

## 持续推进规则

默认持续推进，不轻易停止。

以下情况之外，不应主动结束任务：
- 已达到目标
- 当前方向经过充分验证，确认没有真实增量空间
- 出现无法在本地解决的真实阻塞
- 用户明确要求暂停、转向或结束

以下都不是停止理由：
- 一次实验失败
- 一个方向效果一般
- 中间结果不清晰
- 需要继续拆分问题

## 推荐工作方式

- 开始处理本项目任务前，应先阅读 `docs/skills/carp-project/SKILL.md`，先建立项目上下文，再进入具体执行。
- 一次只改一条清晰的结构或一组强相关逻辑。
- 每一轮修改后都尽快验证。
- 优先做窄修，不先做大而泛的改动。
- 如果局部参数已挖尽，就上升一个层级处理：
  - 参数层
  - 分支层
  - 家族层
  - 路由层
  - 架构层
- 每次失败都要提炼原因，并把原因输入下一轮尝试。

## 卡住时的升级模式

当连续几轮没有有效增量时，应执行以下升级流程：

1. 重新定义当前问题。
2. 找出真实的失败簇或受损对象。
3. 改变攻击层级：
   - 参数 -> 分支
   - 分支 -> 家族
   - 家族 -> 路由
   - 路由 -> 架构
4. 从新的层级继续推进，而不是在旧层级死磨。

## 仓库清洁规则

- 优先直接修改主项目文件。
- 非必要不要保留临时脚本、临时 csv、临时 json、临时 markdown、临时配置文件。
- 临时研究产物使用后应及时清理。
- 除非任务明确要求，不要动 `data/cache`。
- 当 README、命令示例、项目结构说明与当前事实不一致时，应同步更新。

## Cache 不可变红线

如果当前任务要求 `data/cache` 绝对不能变化，后续 session 必须把下面这条当成硬规则：

- 默认禁用一切 `DataFetcher.get_k_data(...)` 路径

原因不是抽象上的“有风险”，而是代码行为本身如此：

- `get_k_data(...)` 在非纯回测路径会检查缓存新鲜度
- 一旦判定缓存“不是最近交易日”，就会抓网络数据
- 然后调用 `_save_to_cache(...)` 写回原缓存文件

因此在“cache 不可变”任务里，只允许两种验证方式：

1. 走正式缓存报告路径：
   - `python3 stock_trading_advisor/main.py --report --new-strategy`
   - 或 `python3 stock_trading_advisor/main.py --report --new-strategy -b 000001 600000`
2. 手工读取缓存 csv，再通过 `analyze_stock(..., df_override=df_raw)` 分析

在这种场景下，以下方式默认视为危险：

- 普通研究脚本里直接 `DataFetcher().get_k_data(...)`
- 未传 `df_override` 的 `analyze_stock(...)`
- 普通 `python3 stock_trading_advisor/main.py -b ...`

如果已经发生 cache 漂移：

- 立即停止继续实验
- 先恢复 cache
- 再重新确认 baseline
- 不允许拿漂移后的结果和旧 baseline 直接比较

## 文档同步规则

- 先阅读 `docs/skills/carp-project/SKILL.md`，理解项目当前原理和结构。
- 如果代码与文档冲突，以代码为准，并更新文档。
- 如果修改代码后会影响文档内容，也要同步更新文档。
- 更新文档时，不要随意改变现有文档的分类、层级和组织方式。
- 文档更新的目标是：
  - 让文档与当前实现一致
  - 保持原有结构稳定
  - 方便后续 session 延续理解

## 未来函数红线

- 禁止使用未来数据。
- 禁止把未收盘的当周/当月数据当成完整周线/月线使用。
- 如果变量名带有 `weekly` 或 `monthly`，必须确认它到底是：
  - 真实高周期数据
  - 还是日线近似值
- 在未确认之前，不允许默认它是安全的。
- 不要基于全量历史数据给股票做静态分类，因为这在回测中等价于把未来信息带入当前决策。
- 不要通过白名单或黑名单直接指定某只股票该用什么策略，这通常属于过拟合。
- 不要按市场类型一刀切，例如简单地按 A 股 / 港股决定策略家族；同一市场内部也可能混有完全不同的股票类型和走势结构。
- 未来函数测试必须覆盖“本轮新增信号”：
  - 新增买点、卖点或路由分支后，必须把对应信号加入 `stock_trading_advisor/tests/test_lookahead_bias_smart.py` 的 `signal_cols` 与 `comparison_cols`
  - 必须验证测试样本里这些新增信号有真实触发（触发次数 `> 0`）
  - 若新增信号触发次数为 `0`，该轮未来函数检测视为“覆盖无效”，不能作为安全结论

## checkpoint / commit 前的必做校验

- 任何准备生成 checkpoint 或 commit 的策略改动，都必须执行：

```bash
source venv/bin/activate && python3 stock_trading_advisor/tests/test_lookahead_bias_smart.py
```

- 如果本轮新增了买点、路由入口或其他可能影响未来函数判断的分支，应同步检查是否需要把新增买点纳入 `stock_trading_advisor/tests/test_lookahead_bias_smart.py`。
- 除了“纳入测试”，还必须确认“被测试样本触发”：
  - 输出新增信号的触发统计（按股票、按信号）
  - 至少保证每个新增关键信号在测试集里有触发；否则补充股票后重跑
- 如果未来函数检测未通过，不允许把该版本作为 checkpoint 或 commit 保留。

## Commit 纪律

- 只提交保留下来的改动。
- 不要把临时研究文件提交进仓库。
- 策略类改动优先使用带性能摘要的 commit 风格。

参考格式：

```text
<标题>

Performance:
- Return: <旧值> -> <新值> (+/-变化)
- tPF: <旧值> -> <新值> (+/-变化)
- Win rate: <旧值> -> <新值> (+/-变化)
- Max drawdown: <旧值> -> <新值> (+/-变化)
```

## 汇报风格

- 先说当前基线。
- 再说本轮做了什么。
- 明确区分：
  - 保留了什么
  - 回退了什么
- 不粉饰失败实验。
- 只要任务还在推进，就优先给出下一步，而不是过早收尾。

## 反模式

以下行为应避免：

- 一次失败后就停止
- 没验证就下结论
- 把多个无关实验混在一起判断
- 为了修一只股票而悄悄打坏全局
- 用全量历史去给股票贴固定标签，或靠白名单/黑名单决定策略归属
- 因为“看起来合理”就保留无增量参数
- 只做分析，不推动代码和验证前进

## 停止条件

只有满足以下任一条件，才应考虑停止：

- 目标已经达成
- 当前方向经过充分验证，确认无空间
- 出现真实外部阻塞，无法继续
- 用户明确要求结束或转向

除此之外，应继续迭代推进。
