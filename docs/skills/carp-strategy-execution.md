# Carp Strategy Execution

本文件只定义执行纪律，不重复介绍项目结构。

项目定位、主线文件、cache 行为事实、命名坑点，先读 `docs/skills/carp-project-description.md`。

## 总原则

- 以目标达成为第一优先级
- 修改代码前，必须先把问题想清楚，至少明确：
  - 根因落点
  - 修改假设
  - 验证口径
- 决定推进后，直接在主策略文件中修改、运行验证、对比结果，再决定保留还是回退
- 不因一次失败就停止
- 不因结果不理想就草率结束
- 必须诚实：如果验证结果不好，就明确说明不好，不能强行解释成有效

## 推进模式与默认流程

本项目的策略优化，至少分两类：

- 窄修迭代
  - 适用于现有主线架构不变，只修某个家族、某条退出链、某批股票或某类坏簇
  - 典型做法是小步试验、快速验证、无增量就回退
- 结构级改造
  - 适用于路由框架重做、持仓/退出框架重做、整体策略替换、引入新的主家族体系
  - 这类任务不应假装成“小修小补”，而应先从大结构想清楚，再往下拆

默认先做：

1. 先确认当前保留基线
2. 明确这一步的目标，以及它属于：
   - 窄修迭代
   - 还是结构级改造

### 窄修迭代路径

1. 先做根因分析，优先定位问题的主轴；常见切入维度包括策略家族、退出链、受影响股票集合和坏簇类型，但不要求每次都按固定顺序把这些维度全部分析一遍
2. 提出下一条窄而清晰的假设
3. 直接在主工作文件中修改代码，除非有充分理由不这么做
4. 运行正式验证
5. 与当前基线对比
6. 如果结果更好，就保留并继续推进
7. 如果结果更差、无增量或副作用过大，就完整回退
8. 重复以上循环，直到达到目标或确认该方向无空间

### 结构级改造路径

1. 先确认为什么当前主线结构不够用，不能只说“想法更大”
2. 先定义顶层方案：
   - 要替换什么
   - 保留什么
   - 新结构的入场、持有、退出、风控分别怎么组织
3. 再把大方案往下拆成可执行子问题，而不是直接在旧参数上微调
4. 优先先打通一条完整主链，再逐步补齐分支和保护逻辑
5. 验证时先看结构是否成立，再看局部坏簇和全量结果
6. 如果顶层方案本身站不住，就整体回退，不要把半套结构残留在主线里

## 分析策略的原则和方法

### 根因优先

- 修改代码之前，必须先尽量分析清楚根本原因
- 优先回答“为什么会这样”，再回答“怎么改”
- 不要一上来就调参数
- 家族、退出链、股票集合、坏簇类型，是常用的定位维度，不是固定顺序检查表
- 先从最能快速缩小问题空间的维度切入：
  - 如果是单股被打坏，先看受损股票和真实交易簇
  - 如果是整体收益结构变差，先看家族和退出链
  - 如果是某一类走势普遍失效，先看坏簇类型和对应过滤条件

### 调研阶段的方法

- 先定义研究对象，不要一上来就泛泛看全局：
  - 是某只股票
  - 某类股票
  - 某个策略家族
  - 还是某种坏簇
- 先看真实交易，再看指标和参数：
  - 先还原它是怎么买进、怎么持有、怎么卖出的
  - 再问是哪一段逻辑导致了当前结果
- 先看对比，再看单点：
  - 受损股票和正常股票对比
  - 当前版本和 baseline 对比
  - 同一家族里好交易和坏交易对比
- 先区分“现象”和“机制”：
  - 现象是“哪只股票坏了、哪类收益掉了”
  - 机制是“哪个家族、哪个过滤器、哪条退出链在起作用”
- 调研结论至少要产出三件事：
  - 当前问题最可能落在哪个层面
  - 为什么会这样
  - 下一步最值得验证的假设是什么

### 调研时优先考虑的方法来源

- 主动做网络搜索，这通常是最重要的方法之一，尤其适用于：
  - 引入新的大类策略
  - 结构级改造
  - 针对某类坏簇做定向提升
- 外部搜索的重点不是照抄参数，而是寻找：
  - 可复用的结构思路
  - 同类形态的常见过滤条件
  - 配套持有 / 退出 / 风控方法
  - 常见失败模式和规避方式
- 优先结合多类外部来源交叉看：
  - 搜索引擎结果
  - GitHub 策略实现
  - 因子或技术分析文章
  - 论文、研报或系统化总结
- 使用项目内资产时，优先结合：
  - 正式报告和受损股票
  - 真实 `entry_reason / exit_reason`
  - 现有测试
  - `stock_trading_advisor/src/factor_library.py`
- 如果外部搜索得到的好思路最终落到“可复用因子”上，不要长期放在临时代码里，应及时沉淀进 `factor_library.py`

### 根因还不清楚时，优先做

- 真实交易簇归因
- 受损股票对比
- 入场 / 退出分支定位
- 因子分布对比
- 运行时路径核对

### 分析层面的设计约束

- 新策略不能只设计入场方案，必须同时考虑配套出场方案
- 结构级改造时，先回答顶层结构是否成立，再进入局部参数或坏簇修补
- 任何新的买点、路由分流、策略家族或持有模式，在进入正式实验前，都应同时回答：
  - 这类单子为什么买
  - 买后什么情况下继续拿
  - 买后什么情况下尽快退出
  - 它与现有止损、trailing、extended hold、趋势转空退出如何配合

## 修改代码与验证策略

### 修改策略的方法

- 修改前先决定这轮到底在改哪一层：
  - 入场
  - 持有
  - 退出
  - 路由
  - 风控
- 一轮只允许一个主要因果假设，不要把多个彼此无关的猜想混在一起
- 小修时，优先做“闭环修改”：
  - 如果新买点会改变持仓行为，同轮就把对应退出和保护逻辑一起考虑
- 大改时，优先做“主链打通”：
  - 先让新结构形成完整的入场、持有、退出闭环
  - 再补次级分支和坏簇修复
- 优先复用现有列、现有 reason、现有执行骨架，除非确认现有结构已经不够用
- 如果新思路依赖新的可复用因子，优先先把因子整理进 `stock_trading_advisor/src/factor_library.py`，再在策略主线里接入
- 不要把从外部搜索得到的好因子长期散落在：
  - 临时脚本
  - 一次性研究代码
  - `new_strategy.py` 的局部临时计算
- 每一轮改动都要能回答：
  - 这轮到底改了什么
  - 预期改善什么
  - 可能打坏什么
  - 用什么验证来证明它有效或无效

### 修改代码的原则

- 优先直接修改主项目文件
- 默认主工作文件是 `stock_trading_advisor/src/new_strategy.py`
- 一次只改一条清晰的结构或一组强相关逻辑
- 结构级改造时，可以一次落一条完整主链或一个连贯子系统，但不要把彼此无关的实验混在同一轮里
- 非必要不要保留临时脚本、临时 csv、临时 json、临时 markdown、临时配置文件
- 如果有效因子值得长期复用，优先沉淀进 `stock_trading_advisor/src/factor_library.py`

### 验证纪律

- 优先使用项目正式验证路径，不使用未经确认的临时判断代替
- 能跑正式回测，就不要只做局部猜测
- 当改动针对特定股票或坏簇时，要显式检查这些目标对象
- 当改动只修某一只股票、某一类股票或某一类坏簇时，必须额外显式检查：
  - 高收益前排股票
  - 被新改动打坏的股票
  - losers 数量
- 必须区分：
  - 局部改善
  - 可以正式保留的全局改善

### 分层验证顺序

窄修迭代时，优先走下面这条由小到大的验证路径：

1. 先深入分析目标股票或目标类型的根本原因
2. 针对性设计策略或修改分支
3. 先做单一股票验证
4. 再做同类型股票验证
5. 再扩到更多相近股票验证
6. 最后再做全部股票正式回测验证

结构级改造时，可以先从大到小推进，但仍要保持验证闭环：

1. 先验证顶层结构假设是否成立
2. 再验证主链是否能形成合理的入场、持有、退出闭环
3. 再检查代表性股票、代表性坏簇和明显高收益股票是否被打坏
4. 最后再做全部股票正式回测验证

### 标准命令

cd carp_proj_2.0

source venv/bin/activate && python3 stock_trading_advisor/main.py --report --new-strategy -b 300293 000001

source venv/bin/activate && python3 stock_trading_advisor/tests/test_lookahead_bias_smart.py

## Cache 不可变任务

如果当前任务要求 `data/cache` 绝对不能变化，把下面这条当成硬规则：

- 不要走任何 `DataFetcher.get_k_data(...)` 路径
- 只使用正式缓存报告路径或 `df_override` 的纯缓存分析口径

这里强调的是执行纪律。  
cache 漂移的根因和代码行为说明，交给 `docs/skills/carp-project-description.md`。

一旦发生 cache 漂移：

- 立即停止继续实验
- 先恢复 cache
- 再重新确认 baseline
- 不允许直接拿漂移后的结果和旧 baseline 比较

## 未来函数与执行价格红线

### 未来函数红线

- 禁止使用未来数据
- 禁止把未收盘的当周 / 当月数据当成完整周线 / 月线使用
- 如果变量名带有 `weekly` 或 `monthly`，必须确认它到底是：
  - 真实高周期数据
  - 还是日线近似值
- 不要基于全量历史数据给股票做静态分类
- 不要通过白名单 / 黑名单直接指定某只股票该用什么策略
- 不要按市场类型一刀切决定策略家族

### 未来函数测试覆盖要求

- 新增买点、卖点或路由分支后，必须把对应信号加入 `stock_trading_advisor/tests/test_lookahead_bias_smart.py`
- 必须验证测试样本里这些新增信号有真实触发（触发次数 `> 0`）
- 若新增信号触发次数为 `0`，该轮未来函数检测视为覆盖无效
- 未来函数检测结果零容忍：
  - 只要存在 `1` 个失败项，该轮即判定“未来函数检测不通过”
  - 未来函数检测不通过时，禁止保留该轮 checkpoint 或 commit

### 交易价格口径

- 本项目回测执行价固定为收盘价（close）
- 盘中高低价、盘中形态只能作为参考信号，不能直接作为成交价或收益计算价
- 新增执行分支时，必须显式区分：
  - `reference`
  - `execution_price`
- 验收时必须检查是否隐式引入了“盘中成交”假设

## Baseline 与 commit 规范

### 基线纪律

- 任何时候都要知道当前保留版是什么
- 所有实验都必须与当前保留基线对比，而不是凭记忆判断
- 实验失败必须完整回退
- 不允许把失败实验半留在代码里
- 禁止把“当前 HEAD 一次回测结果”当成 baseline
- baseline 必须以三元组锁定：
  - `baseline_commit`
  - `当前 cache 全量` 正式报告指标（以报告中的实际股票数为准；当前示例为 `249-stock`）
  - `未来函数检测 0 失败`

### 保留 commit 前的必做校验

1. 运行当前 cache 全量正式回测（`--report --new-strategy`）
2. 对比上一版 baseline commit 的正式报告，至少检查：
   - `avg_return`
   - `tPF`
   - `median`
   - `losers`
3. 运行未来函数检测，必须 `0` 失败
4. 只有在“指标满足保留标准 + 未来函数 0 失败”时，才允许创建 commit
5. 新 commit 创建后，默认把该 commit 作为下一轮 baseline

### Commit 纪律

- 只提交保留下来的改动
- 不要把临时研究文件提交进仓库
- 策略类改动优先使用带性能摘要的 commit 风格

### Commit message 参考格式

```text
<标题>

Baseline:
- commit: <baseline_commit>
- report: <baseline_report>

Performance:
- Return: <旧值> -> <新值> (+/-变化)
- tPF: <旧值> -> <新值> (+/-变化)
- Win rate: <旧值> -> <新值> (+/-变化)
- Max drawdown: <旧值> -> <新值> (+/-变化)

```

说明：

- baseline 保留判断要检查 `avg_return / tPF / median / losers`
- commit message 的 `Performance` 段只写：
  - `Return / tPF / Win rate / Max drawdown`

## 文档同步、汇报与停止条件

### 文档同步规则

- 如果代码与文档冲突，以代码为准，并更新文档
- 如果修改代码后会影响文档内容，也要同步更新文档
- 更新文档时，不要随意改变现有文档的分类、层级和组织方式

### 汇报风格

- 先说当前基线
- 再说本轮做了什么
- 明确区分：
  - 保留了什么
  - 回退了什么
- 不粉饰失败实验

### 持续推进与停止条件

默认持续推进，不轻易停止。

只有满足以下任一条件，才应考虑停止：

- 目标已经达成
- 当前方向经过充分验证，确认没有真实增量空间
- 出现无法在本地解决的真实阻塞
- 用户明确要求暂停、转向或结束
